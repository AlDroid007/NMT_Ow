# Архитектура «НМТ Тренажёр • Сова-Лиза»

## Целевая схема

```
web/  (Vue 3 + TypeScript + Ionic) ──► Cloudflare Pages (сайт)
   │                              └──► Capacitor ──► приложение iOS (App Store)
   └── supabase-js ──► Supabase: Auth (код из почты) + PostgreSQL (RLS) + функции begin/submit_session
nmt_tutor/  (Python + Tkinter) — 🧊 заморожен: эталон для проверки порта и сборка для тестеров
admin (Vue 3, позже) ──► тот же Supabase
```

- **Основной клиент — `web/`**, подробно в [`WEB.md`](WEB.md). Логика тренажёра (задания, проверка,
  подсказки, баллы, кабинет) в нём переписана на TypeScript 1:1 с Python-ядром, описанным ниже.
- **Облако общее** для всех клиентов: схема и права — [`DATABASE.md`](DATABASE.md).
- **Десктоп `nmt_tutor/` заморожен** (без новых функций). Ниже — его устройство; модули ядра служат
  образцом для `web/src/core/`. План — [`ROADMAP.md`](ROADMAP.md).

## Десктоп (Python)

Проект — Python-пакет `nmt_tutor` и файл запуска рядом с ним. Пакет разделён на три слоя:
**ядро**, **хранилище данных** и **интерфейс**. Ядро не знает ни про окна, ни про файлы.

Как запускать на другом компьютере — см. [`ИНСТРУКЦИЯ_ЗАПУСКА.md`](../ИНСТРУКЦИЯ_ЗАПУСКА.md).
Настройка облака — [`CLOUD_SETUP.md`](CLOUD_SETUP.md), план развития — [`ROADMAP.md`](ROADMAP.md).

## Правила слоёв

- **Ядро** (`config`, `data`, `generators`, `engine`, `hints`, `banks`, `profiles`, `cabinet`, `auth`) не импортирует `tkinter`
  и не читает/пишет файлы пользователя. Импортируется без окон за ~20–40 мс.
- **Хранилище** (`storage/`) — единственный слой, который знает пути на диске. Остальной код
  работает только через интерфейс `Repository`.
- **Интерфейс** (`ui_tk/`) получает задания и проверку от ядра, а сохраняет через `Repository`.
  Сам ничего не считает и не пишет на диск (кроме «Сохранить отчёт (.txt)» по выбору пользователя).

## Как это работает вместе

1. **Запуск.** `nmt_tutor_mac.py` → `app.main()` открывает зашифрованное хранилище и создаёт окно
   `NmtTutorApp`. Нет пакета `cryptography` — программа предлагает работать без сохранения
   (`MemoryRepository`).
2. **Профиль.** Первым открывается экран «Хто займається?» (а если профилей ещё нет — короткая форма
   создания: имя и необязательный PIN; остальное — в полной форме «Мій профіль»). Пока профиль не
   выбран, меню содержит только «Файл → Вийти» и «Довідка» (`ui_tk/app._setup_menus` строит меню
   по состоянию). После выбора профиля (и PIN, если он задан) окно получает `self.repo =
   store.for_profile(id)` — дальше все экраны видят только данные этого профиля.
3. **Сессия.** Интерфейс берёт план у ядра (`engine.build_session_plan`), проверяет ответы через
   `engine.evaluate_answer`, подсказки получает из `hints.build_10_hints`. Если ученик выбрал ответ, но
   ушёл с задания без «Перевірити» («Далі →», вкладка предмета, «Завершити тест»), ответ засчитывается
   тихо (`_capture_pending_answer`). Сессия совсем без ответов не сохраняется, и экран результатов
   прямо об этом говорит.
4. **Сохранение.** Сначала сохраняется текст отчёта, затем результат со ссылкой на него
   (`report_id`); всё шифруется и записывается в `~/Documents/NMT_Tutor/nmt_tutor_data.sqlite3`.
5. **Кабинет** (`cabinet.py` считает, `screens/cabinet.py` рисует) строится из сохранённых результатов
   профиля: уровень = средний балл за последние 3 тренировки, график по датам, слабые темы
   (свежие ошибки весят больше), история с открытием отчёта. Кнопка «Потренувати» у слабой темы
   запускает тренировку по одному разделу (`engine.build_section_plan`).
6. **Ключ шифрования** лежит не рядом с базой, а в системном хранилище: Связка ключей на Mac
   (запись `NMT_Tutor`), DPAPI на Windows (файл `.nmt_tutor_key`). Если ключ не подходит, база не
   удаляется, а переименовывается в `.unreadable-…`, и создаётся новая.

## Профили и вход

- Профиль — обычный JSON-словарь (`profiles.py`): `id` (UUID), имя, аватар (эмодзи или ссылка на
  картинку), свои предметы, цели 100–200 по предметам, дата НМТ, `identities` (способы входа),
  `pin` (хэш), `created_at`/`updated_at`.
- Результаты, отчёты и свои банки заданий принадлежат профилю (колонка `profile_id`). Данные,
  накопленные до появления профилей, при создании **первого** профиля переходят к нему.
- PIN: 4 цифры, хранится только PBKDF2-хэш с солью; после 5 ошибок — пауза 30 с (`auth/local.py`).
  Это защита от других людей за тем же компьютером, а не шифрование: ключ базы общий для всех профилей.
  Забытый PIN не восстанавливается — профиль можно только удалить.
- **Google / Apple (позже).** Добавляются как новые `AuthProvider` в `auth/` (на компьютере — OAuth
  через браузер с возвратом на `127.0.0.1`, на iOS — системные кнопки). Они возвращают
  `AuthIdentity(provider, subject, …)`, которая добавляется в `identities` профиля
  (`profiles.link_identity`), а `Repository.find_profile_by_identity` находит профиль при входе.
  Так локальный профиль можно привязать к аккаунту, не теряя результатов. Apple отдаёт имя только
  при первом входе и может скрыть почту, поэтому имя хранится в профиле, а почта не служит ключом.
- **Облачный аккаунт** — способ входа `cloud` (`profiles.PROVIDER_CLOUD`, subject = ID пользователя
  Supabase). Google и Apple позже войдут в тот же облачный аккаунт через Supabase Auth.

## Облако

Настройка — [`CLOUD_SETUP.md`](CLOUD_SETUP.md), таблицы и права — [`DATABASE.md`](DATABASE.md).

- **Локальная база остаётся главной.** Всё сохраняется сначала на компьютере; профиль, подключённый
  к облаку, синхронизируется в фоне: после входа в профиль, тренировки, правки профиля и по нажатию на
  строку статуса в кабинете.
- **Supabase** = PostgreSQL + вход (Auth) + REST (PostgREST). Программа ходит туда обычными HTTPS-запросами
  (`cloud/http.py`), без SDK. В программе лежит только публичный ключ; кто что видит, решают правила
  RLS в базе (`supabase/migrations/`): ученик — только свои строки, админ (таблица `admins`) — всё на
  чтение, без входа — ничего. Напрямую приложение пишет только свой профиль; тренировки, статистику и
  серию дней пишут серверные функции.
- **Вход:** почта → 6-значный код → сессия (access + refresh token). Сессия хранится зашифрованной в
  `meta` (`profile:<id>:cloud`) вместе с курсором синхронизации, временем последней синхронизации и
  данными сервера (`profile_meta.data`: серия дней). Refresh token меняется при каждом продлении, поэтому
  сессия сохраняется и после неудачной синхронизации (`sync.fail`).
- **Одна почта = один профиль** (уникальный `owner` в облачной таблице `profiles`).
- **Тренировка:** `ui_tk/screens/cloud.begin_training` перед любым стартом (обычная, «Потренувати»,
  работа над ошибками). Для профиля с облаком это вызов `begin_session` — без интернета тренировка не
  начинается; для остальных — сразу. Во время тренировки `engine.record_answer` / `record_hint` пишут
  каждый ответ (задание `task_ref`, тема, верно/неверно, «Перевірити» или нет, уровень подсказки, время)
  и каждую открытую подсказку в блок плана; `build_session_result` кладёт их в результат вместе с
  `session_uid` и `started_at`.
- **Синхронизация** (`cloud/sync.py`) в три шага, чтобы база трогалась только из потока окна:
  `prepare` (что отправить) → `exchange` (сеть, в фоновом потоке) → `commit` (отметить отправленное,
  сохранить скачанное). Вверх: профиль (upsert) и каждая неотправленная тренировка через `submit_session`
  (повтор безопасен; старая история создаётся как `imported`). Вниз: профиль, `profile_meta` и
  тренировки с других устройств по серверному `updated_at` с перекрытием 60 с — они пересобираются в
  локальные результаты для кабинета (`result_from_cloud`, слабые темы — из неверных ответов).
  Неотправленная локальная правка профиля важнее скачанной. PIN, отчёты и свои банки в облако не уходят.
- **Восстановление на другом компьютере:** «Хто займається?» → «☁️ Увійти через пошту» → профиль
  скачивается (`fetch_account_profile` → `profile_from_cloud`) и подтягивает всю историю.
- Без `cloud_config.json` (и с хранилищем в памяти) все кнопки облака скрыты, тренировки стартуют без сети.

## Хранение данных

- Таблицы `meta`, `profiles`, `identities`, `results`, `reports`, `custom_banks`; содержимое каждой
  записи — зашифрованный JSON (версия + nonce + шифротекст, AAD = имя таблицы). В открытом виде лежат
  только номера записей, даты и `profile_id` (случайный UUID). Способы входа ищутся по ключевому
  хэшу (`identities.subject_hash`), сами ID Google/Apple в базу не пишутся.
- Версия схемы — `PRAGMA user_version`, миграции в `sqlite_repo.MIGRATIONS` (v1 — исходные таблицы,
  v2 — профили и `profile_id`, v3 — синхронизация: у результатов `uid` (id тренировки в облаке) и
  `dirty` (номер неотправленного изменения, 0 — отправлено), у профилей `dirty`; старая база
  обновляется автоматически, данные сохраняются).
- Записи выводятся по времени создания (`created_at`), а не по номеру: скачанные из облака старые
  тренировки получают большие номера.
- Папку данных можно переопределить переменной окружения `NMT_TUTOR_DATA_DIR`.
- При первом запуске старые файлы (`*.json`, `nmt_report_*.txt`) из папки данных копируются в базу;
  сами файлы не трогаются.

## Режимы запуска

| Команда | Что делает |
|---|---|
| `nmt_tutor_mac.py` | Окно программы (Tkinter) |
| `nmt_tutor_mac.py --cli` | Консольный режим, без окон и без сохранения |
| `nmt_tutor_mac.py --selftest [--out FILE] [--real-keystore]` | Самопроверка ядра, хранилища, профилей и синхронизации (облако в памяти), код выхода 0/1 |
| `python tests/smoke_test.py [--no-gui]` | Самопроверка + прогон окна + синхронизация двух окон |
| `python tests/cloud_integration_test.py` | Схема облака и синхронизация на PostgreSQL + PostgREST в Docker |

## Сборка Windows

GitHub Actions (`build-windows.yml`) при пуше в `develop`/`main` или вручную:
ставит Python 3.13, прогоняет `tests/smoke_test.py --real-keystore` (проверка DPAPI),
собирает `packaging/nmt_tutor.spec`, запускает собранный exe с `--selftest` и выкладывает
архив **NMT_Sova_Tutor_Windows** (Actions → Build Windows app → Artifacts). Если в репозитории есть
`nmt_tutor/cloud_config.json`, он попадает в сборку. Отдельный job `cloud-schema` (Ubuntu) прогоняет
`tests/cloud_integration_test.py`.

В spec модули пакета перечисляются по файлам (`hiddenimports`), потому что генераторы
импортируются по имени во время работы и PyInstaller сам их не находит.

## Как расширять

- **Новый генератор** — функция в `generators/<предмет>.py`, зарегистрировать ключ в
  `generators/__init__.py` (`SUBJECT_GENERATORS`). `selftest` проверит, что генератор принимает
  собственный ответ и даёт 10 подсказок.
- **Новый способ входа** — класс `AuthProvider` в `auth/`, добавить в `auth.available_providers()`;
  экран «Як увійти?» покажет его сам.
- **Новые функции** делаются в `web/` (десктоп заморожен). Веб и iOS — один код (см. [`WEB.md`](WEB.md)).
- **Изменение облачной схемы** — новый файл в `supabase/migrations/` (RLS как у остальных: `owner`
  + чтение для админа; запись — через security-definer функцию), проверка в
  `tests/cloud_integration_test.py`. Новое поле профиля без смены схемы — ключ в `profile_meta.data`
  (пишет сервер) или `client_data` (пишет приложение).
- **Свои банки заданий** скрыты флагом `config.CUSTOM_BANKS_UI = False` (код импорта остался).
